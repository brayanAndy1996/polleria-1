Spec 003 (docs/specs/003-users-pin-login/spec.md), Borrador con revisión 1 del 2026-10-08. ADR 0002 Aceptado (bcrypt 6.0.0, @types/bcrypt 6.0.0). El usuario confirmó el 2026-10-08: sesión en la base sin JWT, PIN 4-6 con Entrar, lista de nombres en /login, 5 intentos/15 min, 16 h, cocina entra con pantalla vacía, PIN fáciles en la 004, admin entra a todas las áreas. Revisar si la spec pasó a Aprobada y qué respondió a las preguntas 10-13.

- Sesión: token aleatorio 32 bytes base64url (43 chars) en cookie `polleria_session`; la tabla sessions guarda solo sha256 hex (token_hash). Sin SESSION_SECRET ni variables nuevas (CONFIG_VARIABLES sigue con 7). Cookie HttpOnly, SameSite=Strict, Path=/, Max-Age=57600, sin Secure ni Domain. 16 h fijas, sin renovación. Login exitoso borra sesiones vencidas de todos.
- requireAuth = createRequireAuth({ sessionService }) → res.locals.auth { sessionId, user, expiresAt } (getAuthContext). Lee roles e is_active de la base en cada solicitud. requireRole(...roles): pasa si hasAnyRole(user.roles, roles) (al menos uno); admin NO pasa implícito, cada ruta lo lista; sin contexto → 401; lista vacía lanza.
- Códigos: INVALID_CREDENTIALS 401, UNAUTHENTICATED 401, FORBIDDEN 403, TOO_MANY_ATTEMPTS 429 (details.retryAfterSeconds + Retry-After), USERNAME_TAKEN 409. OpenAPI 0.3.1 (0.3.0 fue el borrador; la revisión cambió role por roles), securityScheme sessionCookie, esquema UserRoles (minItems 1, maxItems 4, uniqueItems).
- Límite: por usuario existente, en memoria, 5 fallos → 15 min; después cada fallo re-bloquea; éxito resetea; 400 y 429 no cuentan; inexistentes no se cuentan (dummy bcrypt). No por IP (el rewrite de Next no reenvía la IP).
- Modelo: users(id INTEGER autoincr, username varchar32 único minúsculas CHECK patrón, display_name varchar40, pin_hash varchar60, roles VARCHAR(16)[] NOT NULL, is_active, timestamps) y sessions(id, user_id FK CASCADE + sessions_user_id_idx, token_hash varchar64 único CHECK hex, expires_at, created_at). Migraciones 20261008120000-create-users.ts y 20261008120100-create-sessions.ts. PK enteras como convención.
- Revisión 1 (varios roles): elegí columna arreglo y NO tabla user_roles porque "al menos un rol" se garantiza con CHECK (con tabla de unión haría falta disparador diferido), lectura en una fila, UPDATE atómico, sin tabla ni migración extra. CHECK verificados en PG 17.5: users_roles_not_empty `cardinality(roles) >= 1 AND array_ndims(roles) = 1`; users_roles_allowed `roles <@ ARRAY[...]::varchar(16)[]` (rechaza NULL); users_roles_no_duplicates con `cardinality(array_positions(roles,'x')) <= 1` por rol (array_positions funciona con cualquier índice inicial; un arreglo 2-D falla con error 0A000, no de CHECK). La base no exige orden; userRolesSchema (shared) valida, rechaza [] 'Elige al menos un rol.' y repetidos 'No repitas un rol.' y ordena por USER_ROLES (waiter, kitchen, cashier, admin); la API ordena al leer (sortUserRoles). admin combinable con otros roles, sin normalizar (S-003-13). Sequelize: DataTypes.ARRAY(DataTypes.STRING(16)); buscar admins con Op.contains → `roles @> ARRAY['admin']::VARCHAR(16)[]`.
- Áreas web (orden Mozo, Caja, Cocina, Administración): /mozo (waiter, admin), /caja (cashier, admin), /cocina (kitchen, admin), /admin (admin). resolveLandingPath: una sola área → directo; varias → última área del DISPOSITIVO ('polleria:lastArea', de cualquier usuario, S-003-14) si le corresponde; si no → /areas ("¿Dónde vas a trabajar?", nav 'Áreas'). /areas nunca salta a la última área. Enlace 'Cambiar de área' (href /areas) en la barra si tiene más de un área; reemplazó 'Ir a Mozo'/'Ir a Caja'. El admin pasa por /areas la primera vez en cada dispositivo (S-003-15). ROLE_HOME_PATHS se eliminó. Línea 'Juan · Mozo, Cajero'.
- Login con lista pública de activos (username + displayName, sin roles) y teclado de PIN 4-6; recuerda 'polleria:lastUsername'.
- Bootstrap: `pnpm users:create-admin` crea solo roles ['admin'] (S-003-16); otros roles en la 004.
- Web: cliente central frontend/src/lib/api/client.ts, 401 UNAUTHENTICATED → hardNavigate('/login'). RoleGuard({ area }) en el cliente, sin proxy de Next.
- Test helper resetMigrationTables debe borrar también las tablas de dominio; toda spec que agregue tablas debe ampliarlo.

**Why:** la 004 (gestión de usuarios y roles), la Fase 2 (autorización con PIN de admin) y Socket.IO reutilizan estas piezas; la elección arreglo vs tabla de unión y el destino por dispositivo no son obvios leyendo el código.
**How to apply:** en 004 usar requireRole('admin'), USERNAME_TAKEN, UserRoles/userRolesSchema para asignar roles (UPDATE de users.roles), borrar sesiones y conteo al desactivar o cambiar PIN, y decidir si debe quedar al menos un admin activo. Cada endpoint nuevo lista 'admin' explícitamente si corresponde y prueba una persona con dos roles. Ver [[decisiones-modelado]] y [[entorno-verificado]].
